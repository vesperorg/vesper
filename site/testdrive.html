Vesper · VESP · hands-on

Send a private payment to another person, and see what everyone else sees.

Real output from a run on 19 October 2026 on node v0.9.0 with phases 1 to 4 active (ring size 48, testnet-1 settings), two nodes on one PC. Your numbers will differ; the shape will not.

This is the test to run before trusting a word on the other pages. Two wallets, two nodes, one payment each way, then four viewpoints: the sender, the receiver, the receiver's accountant holding only a view key, and a stranger reading the raw chain file. At the end you try to break it.

Setup, about five minutes

Everything below runs in a terminal opened in the vesper folder. On one PC, "Alice" is the normal folder and "Bob" is a second data folder with a second node. On two PCs, Bob runs the same commands on his own machine and points his node at Alice's, see the note at the end of this section.

Alice: wallet and node 1 (mines)
wallet.bat                      (creates data\wallets\default.json, shows Alice's tvsp2... address and her recovery code)
start_node.bat                  (node + explorer at http://127.0.0.1:8880, mining to Alice)
Bob: his own wallet and node 2
python coin.py --data-dir data2 wallet new
start_node2.bat                 (node 2 at http://127.0.0.1:8881, peer of node 1, does not mine)

Bob's commands always carry --node http://127.0.0.1:8881 --data-dir data2. Alice's carry nothing. Keep both node windows open; they are the network. A coin can be spent, or used as a decoy, only once it is 10 blocks old, so a brand-new chain refuses its first payment until 48 such coins exist: about 58 blocks, fifteen to thirty minutes of mining. The wallet tells you plainly when a coin is "not yet 10 blocks old." If your nodes are on testnet-1 instead of a chain of their own, the coins already exist and you skip the wait.

Recorded on node v0.9.0 (44 self-test checks) on 19 October 2026 by python testdrive.py, which runs exactly these steps on two throwaway nodes with a throwaway network of their own (it says "test-drive" where your nodes say "testnet-1"); its folder and port names are shown below as they are in the setup above. Long keys and identifiers are trimmed; block numbers and balances depend on the run and will differ on yours. Test coins are tVESP and worth nothing.
Two real computers on the same Wi-Fi: Alice starts her node with python node.py --host 0.0.0.0 --mine, finds her PC's address with ipconfig, and Bob starts his with python node.py --peer http://ALICES-IP:8880. The nodes talk plain HTTP with no authentication; they now have per-address limits and bans, but they have never met strangers, so keep this to your own network until the public testnet. Do not want to type any of this? testdrive.bat runs the whole test on two throwaway nodes by itself, about five minutes, and deletes its folders afterwards.

The last two lines are phase 4. Alice's node did not shout the payment to everyone; it handed it to one peer, and that peer broadcast it. With two nodes the path is one hop; on a real network it is several, and the node that broadcasts first is not the sender's.

STEP 6What the transaction actually contains

python coin.py tx 1188480b5a815fa7...
txid 1188480b5a815fa7... | transfer | in block 59, 1 confirmation(s) | inputs: 1 | outputs: 2 | fee: 0.00001 tVESP
  input 0  : one of a ring of 48 outputs, e.g. 0385d50fd3..., 05b7e0715e..., 070c1f605f...
            spent marker (key image) 2604d0abeaec4f8ee0d35836...   pseudo commitment 5169bfad7efc6b31...
            signature: c + 48 s-values + D   (which of the 48 it was: not written anywhere)
  output 0 : one-time key 5e33c62aaaec6b...   sealed amount
  output 1 : one-time key c6c5550b04dacb...   sealed amount
  one 736-byte proof that none of the 2 sealed amounts is negative
  size: 9479 bytes of JSON   (add --json to see every field)

The input no longer says which output it spends. It lists 48 existing outputs in sorted order and carries one ring signature proving the signer owns one of them, plus a key image: a one-way marker of the real output that lets every node refuse a second spend without learning which output it marks. The two outputs are sealed, with one 736-byte proof that neither hidden value is negative. Output 1 is the key Bob's wallet recognised in step 3; nothing in this listing says so, and the other output is Alice's change. Which of the 48 was really spent: not knowable from this.

12.5 in, 3 out, the fee gone, 9.49999 of change at a fresh key, locked for 10 blocks like any new coin. The view-key file Bob exported in step 4 carries the key image of the 12.5 output he held then, so his accountant can see that output was spent. The change arrived after the export, so the accountant sees its amount but not whether it has since been spent, until Bob exports a fresh file. That is the honest limit of a view key once senders are hidden.

Now try to break it

Each of these should fail. If one doesn't, you have found something worth the bounty, and the page you are reading is wrong.

Rewrite history

Stop node 2. Open data2\chain.jsonl in Notepad, change one character inside any commitment, range_proof or signature, save, then run python coin.py --data-dir data2 validate.

Expected, from the run: "INVALID: block 59 of the saved chain breaks a rule: txid does not match the transaction contents." Start node 2 again and it logs that block 59 was damaged, keeps the good blocks before it, sets the file aside as chain.jsonl.damaged-<time> and fetches the rest from node 1.

Spend more than you have

As Bob: send vespALICE 50 when he holds 9.49999, still inside the lock.

Expected, from the run: "insufficient funds: have 0 tVESP, need 50.00001 tVESP (amount + fee). Another 9.49999 tVESP is yours but cannot be spent yet: it is less than 10 blocks old, or already in a payment that is waiting to be mined. Try again in a few minutes." Refused before it leaves the wallet.

Spend the same output twice

Send a payment as Bob, and before it is mined send another from the same wallet.

Expected: the wallet refuses to reuse a coin that is already in a waiting payment. Build two payments from one coin by hand and the node refuses the second with "key image already used: that output was spent before (double spend)." The node never learned which output; the marker alone was enough.

Replay a payment

Take the JSON of a confirmed transaction from coin.py tx TXID and post it to a node again.

Expected, from the run: "transaction is already in the chain."

Mistype an address

Change a character in the middle of Bob's address and send 1 VESP to it.

Expected, from the run: "'tvsp2CbacAEbNVawwNbzK3dDwXZWrXY79xEhmqCZXbbCtUcP...' is not a valid tVESP address (they start with 'tvsp' and are long: two keys plus a checksum)." The checksum catches it. (A valid address that is simply the wrong person's is not caught by anything; copy-paste, never retype.)

Spend with a view key

Copy data2\wallets\default.viewkey.json over a spare wallet file and try to send from it.

Expected, from the run: "that is a view-key file: it can watch, not spend."

Follow the money

In the explorer, open block 59 and look at the payment's input. Try to find which output it spent.

Expected: you see 48 candidate outputs and a key image, and no way to pick the real one. Then try the statistical version: decoys are drawn from a measured spending pattern, and an attacker who knows that pattern still names the real coin 2.1% of the time where 2.1% would be fair (python leaktest.py prints the number). This is the known weakness of rings, it is the same one Monero carries, and it is why stage two of phase 3 exists.

Study path: the same ground, six times, deeper each time

Each session is one idea, one thing to run, and one question to keep asking until you can answer it without the page.

1. Blocks and proof of work

Run the learning chain's explorer and watch hashes chain together; change one byte in its chain file and watch validation fail.

Why is it cheap to check a block and expensive to make one, and why does that protect history?

2. Keys and signatures

Run python demo.py and read step 5: a signature that verifies against a key nobody can connect to a person.

What exactly does a signature prove, and what does it not prove?

3. Stealth addresses

Steps 1 to 4 of demo.py, then section 4 of the whitepaper, then steps 3 and 5 of this test.

Why can Bob find his payment and Eve cannot, when both have the same chain?

4. Sealed amounts

Step 6 of this test, then section 5 of the whitepaper: commitments, the balance equation, range proofs.

If nobody can see the numbers, how does the chain know no coins were created?

5. Rings and key images

Step 6 of demo.py, the "spend the same output twice" and "follow the money" exercises, then section 6 of the whitepaper.

How can a node refuse a double spend without knowing which output was spent, and why is a crowd of 48 not enough?

6. The network

Node 2's log, and the two-PC setup. Run python leaktest.py and read the two tables it prints. Then section 7 and the threat model.

Who sees your IP address when you pay, how often can a spy running a tenth of the nodes still guess it, and what does hiding it cost in time?

When you can answer all six questions out loud, you can defend Vesper to anyone. When you find one you can't, that is the next thing we work on.
