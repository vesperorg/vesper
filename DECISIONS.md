# Vesper - decisions log

| Date | Decision | Why |
|---|---|---|
| 2026-10-10 | Name **Vesper (VSP)**, addresses start `vsp` | The founder picked it from a list of names verified free on CoinGecko (Noir, Whisper were runners-up). |
| 2026-10-10 | Privacy is mandatory: there is no transparent transaction type | Zcash's lesson - optional privacy means a small crowd and a leaky chain. |
| 2026-10-10 | Ledger is a set of unspent outputs locked to one-time keys, not accounts | Accounts need public balances; privacy needs outputs nobody can attribute. |
| 2026-10-10 | Curve math in pure Python (`curve.py`), Schnorr signatures | Stealth keys are derived scalars; the `cryptography` library cannot sign with those. ~1.5 ms per key op is fast enough. |
| 2026-10-10 | View keys from day one | Private by default, provable on demand (the compliance story Monero lacks). |
| 2026-10-10 | Phases: 1 stealth addresses (done), 2 hidden amounts, 3 hidden sender (ring signatures first, then a full-chain zero-knowledge membership proof), 4 network-layer privacy (gossip delay) | Each phase is testable on its own and each is a lesson. |
| 2026-10-10 | Speed is a design constraint: every phase reports ms per operation | The founder: "it can't slow down". |
| 2026-10-10 | Learning chain only; never real money; kept separate from any token-sale project | Homemade privacy crypto is unaudited; privacy coins get delisted and would wreck a token sale's legal path. |
| 2026-10-11 | A parallel run of the same conversation built the identical phase 1 under another working name. Kept Vesper; the other working name archived outside this repository (not deleted). | One codebase, one name, one port (8880). |
| 2026-10-11 | Phase 2: amounts sealed in Pedersen commitments; balance proven by a Schnorr signature over the "excess" (inputs - outputs - fee*H) | Lets nodes verify no coins were created without reading an amount. Fee and mining rewards stay public because they must be checkable. |
| 2026-10-11 | Range proofs are Bulletproofs (64-bit), verified per block as ONE batched equation; verified txids are cached | Same proof family Monero uses, 672 bytes. Batching brings a fresh node to 8.4 ms per payment; caching makes mining seen payments nearly free. |
| 2026-10-11 | Curve maths runs on libsodium (PyNaCl) with the readable pure-Python version kept as fallback and as the reference; the self-test cross-checks them | Speed is the hard constraint: 0.11 ms per multiplication instead of 1.5 ms. |
| 2026-10-11 | Every point from the network must be canonical, in the prime-order group, and not the identity | Small-subgroup points are a classic privacy-coin bug class. |
| 2026-10-11 | Every transfer has at least 2 outputs, shuffled; a change output is made even when the change is zero | Uniform shape: nobody can tell payment from change or see "no change". |
| 2026-10-11 | All consensus settings are hashed into the genesis block | Different rules = different coin from block 0, not a confusing failure at block 1. |
| 2026-10-11 | FAIR LAUNCH with a protocol-enforced development fund (the founder's decision, relayed by the sibling session): 10% of each block reward for 4,204,800 blocks to one published address; no premine, no presale | Funds development without selling anything. Off until `coin.py devfund init`. |
| 2026-10-11 | Fund payments are public-amount coinbase outputs with a revealed `ephemeral_secret`; the secret is NOT allowed on ordinary transfers | Anyone can verify the fund was paid. Optional on-chain flags on transfers would make some transactions stand out; payment proofs belong off-chain. |
| 2026-10-11 | `coin.py reset-chain` removes saved blocks only; messages never say "delete the data folder" | Wallets live in `data/wallets`; the old wording could have destroyed the fund wallet. |
| 2026-10-11 | Demo economics (30 s blocks, 50 VSP, halving every 2,000 blocks) are placeholders | Mainnet numbers are a separate decision; at these settings the reward reaches zero in about 3 weeks. |
| 2026-10-11 | Gates before any real value: phases 3 and 4, an independent cryptographic audit, legal advice | Never call it untraceable while a transaction still names the outputs it spends. |
| 2026-10-11 | Ticker **VES**, addresses start `ves` (was VSP / `vsp`) | "Vesper Finance (VSP)" is a listed DeFi token; Claude had checked the NAME on CoinGecko but not the ticker. The sibling session caught it and the founder kept the name. Open concern: VES is also the ISO 4217 code of the Venezuelan bolivar, so price sites and exchanges already use it for a currency; VSPR and VESP are free alternatives. |
| 2026-10-11 | The address prefix is spelling, not consensus: wallets written under an old prefix open under the new one (`convert_address`) | The prefix never reaches the chain, so a ticker change must not strand a wallet or force a new chain. |
| 2026-10-11 | Ticker **VESP**, addresses start `vesp` (VES lasted an hour) | VES is the ISO 4217 code of the Venezuelan bolivar and is already listed as a currency on price sites and exchanges. VESP is free on CoinGecko and DEXes. Changing cost nothing because wallets survive a prefix change. |
| 2026-10-11 | Phase 3, stage one: inputs no longer name an output. Each input is a ring of 16 outputs with a CLSAG ring signature and a key image | Hides which output was spent; the key image (one anonymous marker per output) stops double spends. Same scheme Monero uses today. |
| 2026-10-11 | Nothing is ever removed from the ledger; state = all outputs + the set of key images | Nobody can tell which outputs are spent, so none can be pruned. This is the storage cost of hidden senders. |
| 2026-10-11 | Ring members are referenced by txid:index, sorted, exactly ring_size of them (consensus.ring_size = 16) | Content-addressed references keep the verified-txid cache sound across forks; a fixed size keeps all payments the same shape. |
| 2026-10-11 | Balance still uses the excess signature; each ring input contributes a pseudo output the ring signature ties to the real amount | One rule for ring inputs and fund inputs alike. |
| 2026-10-11 | Key images and one-time keys must be lowercase hex; an output may not reuse a one-time key that already exists | They are compared as text (one spelling only), and a reused key could only ever be spent once: the burning bug. |
| 2026-10-11 | Decoys lean toward recent outputs (rank = n * u^3) | Real spending is mostly recent; even decoys would make the newest ring member the likely real one. Decoy choice is the known soft spot of rings and the reason for stage two. |
| 2026-10-11 | The development fund is a glass box: fund outputs are never ring members and are spent by naming them | Income was already public; this makes spending public too, and keeps publicly-owned outputs out of everyone else's rings. Its change is an ordinary sealed output. |
| 2026-10-11 | A view-key file can carry the key images of the outputs held at export time | A view key alone cannot see spends; this lets an auditor see money leaving, for the outputs it covers. |
| 2026-10-11 | Hash-to-point runs on libsodium with the pure-Python version as the definition; generators verified unchanged | 0.08 ms instead of 0.5 ms; needed once per ring member. |
| 2026-10-11 | Stage two (membership among ALL outputs) is a research milestone, not scheduled code | A crowd of 16 is the weakness. Candidates: curve-tree proofs, or a Merkle tree with a SNARK. No proof system, setup or size is promised. |
| 2026-10-11 | Proof of work is Argon2id (32 MiB, 1 pass) instead of double SHA-256; `consensus.pow` selects it and is hashed into genesis | Raised by the sibling session: SHA-256 is Bitcoin's function, so rented ASIC power could overrun a small chain on day one and laptop miners would be irrelevant. Argon2id cannot run on those machines. Measured here: 10.9 ms per try, ~90 tries/s per core; scrypt was 7x slower for the same memory. |
| 2026-10-11 | Argon2id is an interim choice; RandomX is the likely production algorithm | Argon2id resists ASICs but GPUs keep an edge over CPUs. RandomX closes that, but needs a C library; revisit before any public network. |
| 2026-10-11 | Block ID stays sha256d(header); the work value is separate | IDs must be cheap to compute and compare; only the work check is expensive (and it runs after every cheap check). |
| 2026-10-11 | A node records the tip whose work it has checked (`verified_tip.json`) and skips re-doing work for those blocks at start; `coin.py validate` redoes everything | 11 ms per block adds up (a month of chain = 15 minutes). Block IDs chain into each other, so tampering is still caught without redoing the work. |
| 2026-10-11 | Difficulty starts at 10 bits (min 4); sha256d stays selectable for tests only | ~1,000 tries is ~11 s on one core. |
| 2026-10-11 | REVIEW: the spent marker (key image) is now tied to the output's position, I = x*Hp(txid:index, P); the "no reused one-time key" rule is removed | That rule (mine, from the same day) let an attacker copy the key of a waiting payment, get mined first, and cancel the payment for one fee. Position-bound markers are Zcash's fix for the same class of flaw and make the rule unnecessary: a repeated key is simply two coins. |
| 2026-10-11 | REVIEW: wallets keep a ring memory (encrypted with a key made from the wallet's secrets) and reuse the ring on a retry | Two attempts with fresh decoys share exactly one output, the real one. |
| 2026-10-11 | REVIEW: transactions carry no timestamp; mempool ties are broken by arrival order | The creation time to the second was a free leak and a wallet fingerprint. |
| 2026-10-11 | REVIEW: minimum fee = min_fee x max(1, inputs + outputs - 2); wallets pay exactly that | A flat fee made stuffing the permanent ledger with 16 outputs as cheap as one payment. Exact-minimum fees keep wallets indistinguishable. |
| 2026-10-11 | REVIEW: validation writes to a scratch layer (StateView) over the ledger instead of copying the ledger | The copy cost grew with the chain: every block and every waiting payment paid for every output ever made. Now 0.03 ms on a 200,000-output ledger. |
| 2026-10-11 | REVIEW: blocks this node already checked are not re-verified (work or signatures) on restart or when switching branches; peers are caught up with only the new blocks | Before, falling one block behind meant downloading and re-checking the whole chain. Block IDs chain into each other, so skipping is safe; `coin.py validate` redoes everything. |
| 2026-10-11 | REVIEW: difficulty is an integer number of tries, recomputed every block from the last 30 (work / time x target), clamped to x2 or /2 per block | Whole-bit steps every 10 blocks left block times anywhere between 15 and 60 s. `difficulty_window: 0` fixes the difficulty (tests). |
| 2026-10-11 | REVIEW: the node checks Host and Origin on every request, grants no cross-site access, allows miner control only from the same computer, hides the reward address from peers, and believes a claimed node address only if the connection comes from it | A web page could start or stop the miner or redirect its rewards (cross-site request, DNS rebinding); any peer could read the owner's wallet address; a lying peer could make the node fetch from an address of its choosing. |
| 2026-10-11 | REVIEW 2: difficulty is now a per-block step, previous x 2^((target - solve time) / 600 s), integer maths (the cubic 2^x of Bitcoin Cash's aserti3-2d), one block limited to x2 or /4; `difficulty_halflife_seconds` replaces `difficulty_window` (0 = fixed, for tests) | The 30-block average from the first review still drifted 40% off in a live run and has a known flaw: when a burst of fast blocks leaves the window the difficulty swings again, and hit-and-run miners time that. | 2026-10-11 | REVIEW 2: step form, NOT the schedule-anchored ("absolute") ASERT that Bitcoin Cash uses | The anchored form keeps a calendar: a chain that was off for a day owes a day of blocks and pays them back at minimum difficulty (2,935 blocks in 30 minutes in the simulation, 60 is normal). With the /4 limit the step form produces 98. Cost: the cubic rounding error can add up, bounded at about 0.4% by the feedback loop. |
| 2026-10-11 | REVIEW 2: after losing 90% of miners the chain is slow for about 40 minutes (300 s, 220 s, 176 s ... under 45 s after 28 blocks). Not fixed | No rule that only looks at past blocks can do better without a shorter half-life (noisier, more hopper profit). The known alternative makes the target ease in real time while a block is late; it rewards lying about the clock and no major coin runs it. Research, not scheduled. |
| 2026-10-11 | REVIEW 2: transaction tree hashes leaves and inner nodes with different prefixes and moves an odd node up unchanged | Bitcoin pairs an odd node with a copy of itself, so a block and a twin with a repeated transaction share an ID (CVE-2012-2459). |
